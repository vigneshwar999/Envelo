Judges' Q&A — Sealed Invoices

Arc Builder Program · the ten questions most likely to come up, with answers you can say in about twenty seconds each

Skim this once before the Q&A. Every answer is honest about what is and is not built — reviewers reward that more than polish. The bold phrase in each answer is the one line to land.

Q1 Why does this need a blockchain at all?

Because "paid" should be checkable without trusting us. The invoice itself stays private, but its fingerprint and paid status live on a public network that our server cannot edit — so the proof does not depend on believing the company behind the app. Everything that doesn't need that guarantee deliberately stays off the chain.

Q2 What exactly ends up on the chain?

The anchor stores a scrambled invoice reference, the document's SHA-256 fingerprint — the wax stamp — and the time it was stamped; payment later flips a paid mark next to it. The document itself — names, line items, rates — never leaves the sealed envelope, and a fingerprint cannot be reversed back into the document.

Q3 So the payment amount is public?

Yes — a payment is an ordinary transfer on a public network, so the amount and the wallet addresses are visible; that is exactly what makes the receipt checkable. What stays private is everything the invoice says and who the people are — the app never publishes which person owns which wallet. Private paperwork, public receipt — each where it belongs.

Q4 What happens if a user loses their key?

Three layers, from gentle to last resort. The dashboard makes a passphrase-locked backup file that restores the key on any device, and while a key still works the user can switch to a fresh one — the app re-wraps every stored copy in one atomic step, so everything that opens today still opens under the new key. If the key is truly gone, a typed-RESET issues a new one: old envelopes stay sealed until each counterparty re-shares with one click, but payments and onchain records are untouched.

Q5 Can you — the people running the server — read the invoices?

No. Sealing happens in the sender's browser, so our database holds only sealed envelopes and locked key copies — there is no admin key. That is also why lost keys were a real problem we had to engineer around: a system where we could "just recover it" would be a system where we could read everything.

Q6 Why custodial wallets? Isn't that against the point?

It is a disclosed testnet shortcut: holding the demo wallet keys server-side means anyone can try the app with nothing installed — and the app says this out loud. It is already loosening: a user can enter their own payout address, and payments then land there instead of the app-managed wallet; earlier balance can be moved out with a permanent receipt. To be precise: the app trusts the address the user types — it does not yet make them prove they hold its keys — and with real money, custodial keys would be unacceptable.

Q7 What happens if your server disappears?

The proof outlives us: fingerprints and payment records sit on a public network with a public read function, so they stay checkable without our server. The sealed envelopes are stored by us the way any service holds files, so the honest trade-off is availability, not privacy — if we vanish, an unopened backup may become unreachable, but nobody gains the power to read it.

Q8 What would change on mainnet?

The flow stays the same; the money and the duty change. Test USDC becomes real dollars, so the custodial shortcut must be replaced by wallets users control, and running it becomes a real financial service with the obligations that follow. Today's build is deliberately a testnet demo, says so in the app, and never fakes a receipt to look more finished than it is.

Q9 Why Arc specifically?

On Arc the network fee is paid in USDC itself, so the invoice, the fee, and the balance are one unit — a client needs no second coin before they can pay, which is one less thing to explain to a non-crypto user. And every anchor and payment is an ordinary transaction on a public explorer, so "paid" is checkable rather than claimed. The argument is simplicity, not price talk.

Q10 You revoked the accountant's access — but she already saw it. What did revoke actually do?

It ended her future access through the app: from now on the server refuses to hand her the envelope or her key copy, and a share's built-in expiry (24 hours in the demo) ends access the same way. What it cannot undo is the past — someone who opened or saved a copy while access was live keeps what they took, exactly like paper. Revoke and expiry stop the next look; nothing can repossess the last one, and we say so plainly.
